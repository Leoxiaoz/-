## 0. 文档定位与边界

本文件回答一个问题：**我们到底要做什么游戏。**

- 本文件定义：游戏定位、核心玩法循环、玩家角色、各系统"存在的目的"与彼此关系、胜负/目标体系。
- 本文件**不**定义：具体字段结构（见 `DATABASE_SPEC.md`）、模拟算法细节（见 `SIMULATION_SPEC.md`）、存档读写机制（见 `SAVE_SPEC.md`）、开发顺序（见 `ROADMAP.md`）。
- 本文件**不得**出现任何写死的真实球队 / 球员 / 联赛数据。真实世界的足球内容一律来自数据库（见 `DATABASE_SPEC.md`）。

### 标记约定

- `[已定]` = 已由制定者明确决定。
- `[TBD]` = 尚未决定，或会显著影响架构 / 数据结构 / 存档兼容 / 模拟行为，**需制定者决策**。所有 `TBD` 在文末汇总。
- `[建议]` = 本文档给出的候选方案，仅供参考，**不等于已决定**。

## 1. 游戏定位 `[已定]`

- 类型：**单机**足球经理 / 足球世界模拟游戏。
- 平台：**移动端优先**，终态目标为 **Android App**（可用于 TapTap）。
- 表现：**文字 / 数据驱动**，UI 服务于信息，而不是视觉表现。
- 体验方向：**长期职业生涯**，可跨越多赛季、数十年。
- 世界观：**真实足球世界方向**，但通过数据库导入，引擎不写死真实数据。
- 可扩展：支持**独立数据库**；**后续考虑 Mod**。
- 技术路线（第一阶段）：HTML5 + CSS3 + JavaScript，不使用 Unity / Godot。
- 定性：HTML 版本是**正式游戏的第一代客户端**，不是一次性 Demo。

### 架构红线（定位层面）

- UI 与游戏核心逻辑**必须分离**。
- 数据与逻辑**必须分离**。
- 游戏核心是**数据驱动的足球世界模拟**，不是视觉表现。

## 2. 核心玩法循环 `[已定]`

玩家在一个赛季内的循环：

```
创建 / 选择球队
   → 管理球队
   → 训练球员
   → 制定战术
   → 参加比赛
   → 处理转会
   → 处理合同
   → 管理财政
   → 培养青训
   → 参加联赛 / 杯赛
   → 赛季结束
   → 进入下一赛季（回到"管理球队"）
```

- 外循环：赛季 → 下一赛季，长期延续（见 §15）。
- 内循环的具体推进粒度（按天 / 按周 / 按比赛日推进）`[TBD]`，且会影响存档结构，需决策。

## 4. 球队管理

**目的**：让玩家对一支俱乐部的日常事务有统一的操作入口，是内循环中的枢纽系统。

- 范围（候选）：阵容选择、首发/替补、队长、训练安排、日程推进、职员管理、财政入口。
- 与其他系统关系：向上受联赛/赛事赛程驱动；向下驱动比赛、训练、转会、财政、青训。
- `[TBD]`：具体可操作项清单（哪些是玩家手动、哪些可委托 AI 助教）。
- `[TBD]`：日程推进的控制方式（手动点继续 / 自动推进到下一节点）。

## 5. 球员系统

**目的**：用多维数据描述球员，使同总评的球员也能表现出差异，为比赛模拟与成长提供输入。

- 原则：球员**不能只用总体评分表示**。
- 维度方向（依据项目规则，具体清单见 `DATABASE_SPEC.md`）：技术 / 身体 / 精神属性、位置适性、战术特质、性格、潜力、稳定性、职业素养、野心、伤病倾向、士气、状态、体能、人际关系。
- 与其他系统关系：被比赛模拟读取（见 `SIMULATION_SPEC.md`）；被成长 / 训练 / 青训写入（见 §11、§16）。
- `[TBD]`：属性集合的最终粒度与取值范围（属数据结构核心，需在 `DATABASE_SPEC.md` 阶段决策）。

## 6. 战术系统

**目的**：让战术产生真实的模拟后果，而不是只改一个隐藏加成。

- 原则：战术指令应影响实际模拟行为。
- 方向（候选）：阵型、防线高低、逼抢、节奏、宽度、传球风格、出球/推进方式、攻防转换、球员角色、防守职责、进攻套路。
- 与其他系统关系：作为比赛模拟的高权重输入；受球员位置适性与角色适配约束。
- `[TBD]`：战术指令的最小可用集合（第一阶段做哪些）。
- `[TBD]`：角色/职责体系如何与球员属性映射。

## 7. 比赛模拟

**目的**：核心乐趣来源之一。将"能力+位置+战术+体能+状态+士气+对手+主客场+随机因素"合成为可解释的比赛过程与结果。

- 输入方向（依据第 4 步）：球员能力、位置、战术、体能、状态、士气、对手、主客场、随机因素。
- 输出：比赛过程（事件流）→ 比赛结果（比分、数据、伤病、牌）。
- 与其他系统关系：消费球员/战术；产出结果供联赛/杯赛排名、球员成长、财政、新闻使用。
- 详细规则见 `SIMULATION_SPEC.md`。
- `[TBD]`：比赛模拟的"抽象层级"（离散事件流 vs 回合制 vs 时段比分生成）——**这是本项目的关键技术决策之一**。
- `[TBD]`：玩家是否可在比赛中做临场调整（换人、变阵）。

## 8. 联赛与杯赛

**目的**：为世界提供稳定的竞争结构与时间骨架。

- 范围：联赛（积分制）、杯赛（淘汰/小组）。
- 与其他系统关系：赛程驱动日程；结果驱动排名与晋级；排名驱动财政、声望、AI 行为。
- 规则（升降级、赛制、名额）来自数据库的赛事规则，不写死。
- `[TBD]`：第一阶段实现哪些赛事结构（单联赛？是否含杯赛？）。
- `[TBD]`：多国家 / 多层级联赛是否在早期实现。

---

## 9. 转会与合同

**目的**：让球员流动成为"谈判"，而非"点击购买 → 加入"。

- 原则（依据第 4 步）：转会 = 球队需求 + 球员意愿 + 合同 + 身价 + 工资 + 球队声望 + 竞争球队 + 经纪人 → **谈判**。
- 合同：薪资、年限、奖金、解约条款、续约与到期。
- 与其他系统关系：受财政与声望约束；影响阵容与 AI 建队；产生转会历史（存档内容）。
- 详细规则见 `SIMULATION_SPEC.md`。
- `[TBD]`：转会窗 / 谈判回合机制的具体形式。
- `[TBD]`：经纪人系统是否在早期实现。

---

## 10. 财政系统

**目的**：给俱乐部的所有决策加上资源约束，并在长期内保持稳定（不崩、不通胀）。

- 范围（候选）：收入（门票、转播、赞助、奖金）、支出（工资、转会、运营）、预算分配、盈亏。
- 与其他系统关系：约束转会与合同；受成绩与联赛层级影响。
- 红线：长期模拟下财政**不得崩坏、不得指数膨胀**。
- `[TBD]`：货币单位与量级体系（需与数据库数值口径统一）。
- `[TBD]`：财政复杂度（是否含赛季结算、债务、所有者注资）。

## 11. 青训系统

**目的**：让俱乐部能持续产出新生代球员，支撑长期世界演化。

- 范围（候选）：青训招募、青训梯队、青年比赛、提拔到一线队。
- 与其他系统关系：产出年轻球员 → 进入球员成长系统；受设施与教练影响。
- `[TBD]`：青训产品的生成方式（程序化生成 vs 数据库预设 vs 混合）。
- `[TBD]`：青训在第二阶段还是第三阶段实现（见 `ROADMAP.md`）。

## 12. 教练与工作人员

**目的**：为球队提供能力加成与 AI 行为载体（AI 球队也有主教练）。

- 范围（候选）：主教练、助教、体能/门将/青训教练、球探、队医。
- 与其他系统关系：影响训练效果、球员成长、战术执行、AI 决策风格。

## 13. AI 球队

**目的**：让**没有玩家参与的球队也自己活着**，这是本项目最重要的特色方向。

- 原则：不做"世界暗中帮助或惩罚玩家"的操纵；AI 决策来自自身处境。
- AI 可自主进行：买人、卖人、续约、提拔青训、换教练、改战术、培养球员、管理财政、应对成绩与伤病、争夺荣誉。
- 决策输入方向：俱乐部声望、财务状况、阵容需求、教练理念、联赛排名、董事会预期、青训、转会/工资预算、球员可得性、战术需求。
- 红线：**不得所有 AI 行为一致**。
- 与其他系统关系：消费转会/合同/财政/战术/成长几乎全部系统；是世界持续演化的引擎。
- 详细规则见 `SIMULATION_SPEC.md`。
- `[TBD]`：AI 决策的"评估-行动"模型（效用函数 vs 规则库 vs 混合）。
- `[TBD]`：AI 计算量与移动端性能预算的平衡（见 `ROADMAP.md` 性能约束）。

## 14. 新闻与事件

**目的**：把世界的变化翻译成玩家能读懂的信息，支撑可解释性。

- 范围（候选）：转会新闻、伤病、成绩、奖项、董事会、球迷情绪。
- 与其他系统关系：只读消费其他系统产生的状态变化，不反向操纵结果。
- 红线：若引入脚本化事件，必须显式设计并文档化，不得暗中操纵。
- `[TBD]`：第一阶段的新闻深度（纯信息流 vs 带决策影响）。

## 15. 多赛季世界模拟

**目的**：保证游戏在数十个赛季后依然稳定、可玩、合理。

- 要求：世界独立于玩家持续演化（AI 俱乐部、教练更替、球员更替、财政波动、赛事推进）。
- 稳定性检查项：财政不崩、年龄不越界、无重复/丢失球员、无不可能转会、无空阵容、联赛规模正确、赛程正确、无指数通胀与属性通胀、合同不损坏、数据库不腐坏。
- 与其他系统关系：是所有系统的长期总检验。
- 详细规则见 `SIMULATION_SPEC.md`；测试要求见 `ROADMAP.md`。
- `[TBD]`：目标稳定时长（游戏内多少年必须稳定）与验收口径。

## 16. 球员退役与新生代

**目的**：保证世界球员池在数十年内不断代、不膨胀、不重复。

- 范围：退役判定、老将衰退、新生代生成（青训 + 世界生成 + 数据库预设的衔接）。
- 与其他系统关系：退役移除球员 → 新生代补入 → 维持联赛人数与年龄结构。
- 红线：不得出现不可能年龄、重复球员、无来源球员。

## 20. 约束回顾（红线）

1. 不把真实球队 / 球员 / 联赛写死在代码里。
2. UI 与核心逻辑分离；数据与逻辑分离。
3. 不擅自动摇既有架构；重大结构调整先说明理由与影响。
4. 不破坏存档兼容。
5. 不忽略测试。
6. 不擅自扩大项目范围（无未获批准的多人在线/变现/3D 等）。
7. 世界不暗中操纵以取悦或惩罚玩家。
8. **技术实现必须服务于游戏设计**：不得为降低开发难度而擅自简化核心玩法。若某系统实现复杂，**应先提出简化方案供制定者选择**，而不是直接删除、弱化或替换核心设计。
