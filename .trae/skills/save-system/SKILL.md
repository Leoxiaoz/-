# Save System（存档系统规约 · 项目专属）

> 版本 v1.0（项目定制） · 依据：SAVE_SPEC.md / DATABASE_SPEC.md / GAME_DESIGN.md / SIMULATION_SPEC.md
> 本 Skill 是本项目的**存档红线**，不是通用教程。

## 0. 项目事实（前提，不得违背）

- **数据库 ≠ 存档**：数据库是世界的初始配置，存档是正在运行的世界。
- 存档**必须保存**：当前日期 / 赛季、球员状态、球员成长、转会、合同、财政、联赛排名、比赛结果、AI 球队变化、世界事件、伤病、AI 决策。
- 结构原则：**引用（稳定 ID）+ 增量**，不整库复制。
- **版本化 + 迁移**：旧档必须可正常读写、不崩溃。
- 损坏档需**兜底恢复**，任何自动修复**先备份原档**。
- 导入 / 更换数据库**不得自动覆盖存档**。

## 1. 何时使用

- 设计或修改存档结构。
- 判断"哪些运行时状态需要持久化"。
- 存档版本升级与数据迁移。
- 换库 / 导入数据库后的兼容处理。
- 确定存档读写时机。

## 2. 核心原则（项目专属）

1. **数据库与存档严格分离**。
2. **引用 + 增量**：以 ID 指代数据库实体，只存运行时变化。
3. **状态一致性**：关键状态在创建 / 存档 / 读取 / 跨赛季推进后必须一致；缺省字段有兜底。
4. **版本 + 迁移**：结构变更必须带版本号与迁移策略。
5. **损坏容错**：读取须校验；损坏档可回退 / 修复，且**先备份**。
6. **换库隔离**：不自动覆盖存档；策略须由制定者选定。

## 3. 必须检查什么（检查清单）

- [ ] 新增的运行时状态是否已纳入存档保存范围？
- [ ] 是否用 ID 引用，而非复制整份数据库实体？
- [ ] 读档后状态是否与存档前一致？缺省字段是否有兜底？
- [ ] 结构变更是否带版本号 + 迁移函数？
- [ ] 旧档能否正常读写、不崩溃？
- [ ] 读档是否校验（完整性 / 引用完整性 / 范围合法性）？错误是否分级（致命 vs 可修复）？
- [ ] 损坏档能否回退？自动修复是否先备份？
- [ ] 换库是否有明确兼容策略？是否提示玩家影响？
- [ ] 写入时机是否合理（不丢进度、不高频落盘）？

## 4. 禁止做什么

- 禁止把数据库当作存档，或反之。
- 禁止在导入 / 更换数据库时覆盖玩家存档。
- 禁止无版本号 / 无迁移策略的结构变更。
- 禁止静默忽略或丢弃损坏数据。
- 禁止无备份的自动修复（不得不可逆破坏玩家数据）。
- 禁止让存档在长期（到 2040 年量级）运行下崩溃。
- 禁止自行决定仍标 TBD 的存档设计（已定项见 `DECISIONS.md`）：
  - 物理形态 V1、历史保存策略 V2、存档槽 V3、写入时机 V4
  - 一致性校验粒度 V5、数据库缺失行为 V6、迁移机制 V7、校验分级 V8、回退策略 V9
