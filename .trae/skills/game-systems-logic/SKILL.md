# Game Systems / Simulation（游戏系统与模拟规约 · 项目专属）

> 版本 v1.0（项目定制） · 依据：GAME_DESIGN.md / SIMULATION_SPEC.md / DATABASE_SPEC.md / SAVE_SPEC.md / ROADMAP.md
> 本 Skill 是本项目的**系统设计与模拟红线**，不是通用教程。

## 0. 项目事实（前提，不得违背）

- **四大核心**：比赛模拟、球员成长、转会、世界模拟。这四者决定游戏"灵魂"。
- 比赛引擎**必须模块化**，可拆为可独立替换的阶段：Match Setup / Team Strength / Tactical Effects / Player Interactions / Match Events / Goal Generation / Substitutions / Injuries / Cards / Statistics / Post-match。
- 模拟红线：随机**不替代**逻辑；结果**可解释**；战术有**真实后果**；AI **自主且不一致**；长期**不崩、不通胀、不断代**。

## 1. 何时使用

- 设计或实现任一游戏系统（比赛、球员成长、转会、合同、财政、青训、联赛/杯赛、AI 球队、新闻事件、世界模拟）。
- 讨论系统间数据流、耦合与接口。
- 修改模拟规则、数值、概率模型。

## 2. 核心原则（项目专属）

1. **系统单一职责**，通过明确接口交互，**不直接改他系统内部状态**。
2. **模拟一致性**：结果由模型推导得出；随机性只用于制造不确定性。
3. **可解释性**：重要结果必须能回答"**为什么**"（为何赢/输、为何成长、为何不开心、AI 为何做这笔转会）。
4. **确定性**：同一（数据库 + 存档 + 比赛条件 + 种子）必须可复现。
5. **战术必须有真实后果**，影响实际模拟行为，而非只改隐藏加成。
6. **转会 = 谈判**：球队需求 + 球员意愿 + 合同 + 身价 + 工资 + 声望 + 竞争球队 + 经纪人 → 谈判；**不是**"点击购买 → 加入"。
7. **AI 自主**：基于自身处境决策，**不得所有 AI 同质**，**不得操纵结果服务玩家**。
8. **长期稳定**：防财政崩坏、防指数/属性通胀、防球员断代、防重复/丢失球员。
9. **技术服务于设计**：不得简化核心玩法；复杂时先提简化方案。

## 3. 必须检查什么（检查清单）

- [ ] 系统边界是否清晰？是否直接改动了其他系统的内部状态？
- [ ] 数据流是否明确（输入 / 处理 / 输出；触发式还是轮询式）？
- [ ] 随机性是否作用于**已建模的概率**，而非替代逻辑？
- [ ] 重要结果是否可解释？能否给出成因？
- [ ] 是否可复现（可控种子）？
- [ ] 战术是否影响了真实模拟行为？
- [ ] 转会是否走"谈判"模型而非直接加入？
- [ ] AI 决策是否差异化、是否来自自身处境？
- [ ] 数值在长期（1/5/10/20+ 赛季）是否会通胀或崩坏？
- [ ] 比赛引擎各阶段是否可独立替换？

## 4. 禁止做什么

- 禁止用纯随机决定比赛/事件结果。
- 禁止把战术降为隐藏系数、把转会降为"点击购买"、把 AI 做成全体同质。
- 禁止产生无法解释的黑箱结果。
- 禁止为取悦/惩罚玩家而操纵模拟结果。
- 禁止在系统里硬编码真实足球数据。
- 禁止自行决定仍标 TBD 的模型（比赛抽象层级 S1/T6、AI 决策模型 S13/T12、战术最小集合 S6/T5、实力聚合 S7、战术克制 S8、状态/体能/士气耦合 S9、机会-进球模型 S12、长期收敛 S14）。
- 禁止为省事删除 / 弱化 / 替换核心系统。

## 5. 与其他 Skill 协作

| Skill | 协作方式 |
|---|---|
| `game-architecture` | 分层与模块边界由它定；本 Skill 在边界内实现逻辑 |
| `database-data-modeling` | 模拟读取静态数据；属性粒度/实体模型由它定 |
| `save-system` | 模拟产出的运行时状态（成长、伤病、排名、结果等）需它持久化 |
| `testing-qa` | 多赛季稳定性、确定性复现由它验证 |
| `performance` | AI / 大规模模拟的性能预算由它把关 |
| `mobile-ui-ux` | 模拟结果如何呈现给玩家（可解释性 UI） |
| `documentation` | 规则与数值模型变更必须同步文档 |
