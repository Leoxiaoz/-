# Game Architecture（游戏架构规约 · 项目专属）

> 版本 v1.0（项目定制） · 依据：GAME_DESIGN.md / DATABASE_SPEC.md / SIMULATION_SPEC.md / SAVE_SPEC.md / ROADMAP.md
> 本 Skill 是本项目的**架构红线与评审流程**，不是通用教程。

## 0. 项目事实（前提，不得违背）

- 单机足球经理 / 足球世界模拟；**移动端优先**；终态 Android App（TapTap 方向）。
- 第一阶段技术栈：**HTML5 + CSS3 + JavaScript**；不使用 Unity / Godot。
- HTML 客户端是**正式第一代客户端**，不是一次性 Demo。
- 三条强制分离：**UI ↔ 核心逻辑**、**数据 ↔ 逻辑**、**数据库 ↔ 运行时状态**。
- 游戏核心 = **数据驱动的足球世界模拟**，不是视觉表现。

## 1. 何时使用

- 新增或调整模块、目录、分层边界、数据流。
- 规划、评审或重构工程结构。
- 判断"某功能应放在哪一层"。
- 任何大规模改动之前。

## 2. 核心原则（项目专属）

1. **分层与单向依赖**：表现层（UI）依赖核心模拟层（Core）；Core **不得**依赖 DOM / `window` / 浏览器 API。数据访问（数据库加载、存档读写）为独立层，Core 通过**接口**使用它，不直接碰文件 / 存储 API。
2. **核心可独立于 UI 运行与测试**：Core 必须能在无 DOM 环境下被调用，以支持确定性测试。
3. **数据与逻辑分离**：逻辑中不得硬编码体育数据（国家/联赛/球队/球员/教练/球场/赛制/转会记录/数值）。
4. **数据库与运行时状态分离**：Core 只处理"加载后的世界模型 + 运行时状态"，不关心其来源是 `.fdb` 还是存档。
5. **模块可替换**：比赛模拟、AI、成长等应模块化，允许替换单模块而不重写整体。
6. **确定性**：核心模拟接受**可控随机种子**，同样输入可复现。
7. **技术服务于设计**：不得为降低开发难度而简化核心玩法；复杂时**先提简化方案**供制定者选择。

## 3. 必须检查什么（检查清单）

- [ ] 新代码落在正确层级？有无跨层直接调用？
- [ ] Core 是否误引入 DOM / 浏览器 API / 存储 API？
- [ ] 是否有硬编码的足球数据或魔法数字？
- [ ] 是否把数据库静态数据与运行时状态混在一起？
- [ ] 变更是否破坏既有接口 / 既有模块边界？
- [ ] 是否影响存档兼容（→ 转 `save-system`）？
- [ ] 是否可确定性测试（种子可控）？
- [ ] 是否引入了未获批准的大型系统或依赖？
- [ ] 结构变更是否同步了 `documentation`？

## 4. 禁止做什么

- 禁止把核心逻辑塞进 UI 层，或反之。
- 禁止在逻辑中写死真实足球数据或魔法数字。
- 禁止用显示名作为实体引用 / 主键（须用稳定唯一 ID）。
- 禁止无理由重构已正常工作的系统。
- 禁止擅自决定仍标 **TBD** 的结构（目录布局、ID 形态、加载接口形态、比赛抽象层级等）。
- 禁止引入 Unity / Godot 或未获批准的大型依赖 / 在线服务。
- 禁止为了省事弱化 / 删除 / 替换核心设计。

## 5. 与其他 Skill 协作

| Skill | 协作方式 |
|---|---|
| `game-systems-logic` | 它负责系统内部逻辑；架构只定**边界与依赖方向** |
| `database-data-modeling` | 静态数据结构与 `.fdb` 加载归它；架构确保 Core 只经接口访问 |
| `save-system` | 运行时状态持久化归它；架构负责"哪些状态属于运行时"的边界 |
| `testing-qa` | 架构须保证可测；测试方案由它执行 |
| `mobile-ui-ux` | 表现层规范归它；架构负责 UI 与 Core 的隔离 |
| `performance` | 性能评审由它；架构须预留可优化空间 |
| `documentation` | 结构/接口变更必须同步文档 |
