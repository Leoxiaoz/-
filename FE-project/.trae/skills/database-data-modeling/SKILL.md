# Database / Data Modeling（数据库与数据建模规约 · 项目专属）

> 版本 v1.0（项目定制） · 依据：DATABASE_SPEC.md / GAME_DESIGN.md / SAVE_SPEC.md / SIMULATION_SPEC.md
> 本 Skill 是本项目的**数据建模红线**，不是通用教程。

## 0. 项目事实（前提，不得违背）

- **游戏本体 ≠ 足球数据库**：引擎提供规则与模拟系统，数据库提供足球世界。
- 实体关系链：`Player → Contract → Club → League → Competition`。
- `.fdb` 结构（字段细节尚未定死）：

```
2026_27.fdb
├── manifest.json
├── countries.json / leagues.json / teams.json / players.json
├── managers.json / stadiums.json / competitions.json / contracts.json
└── assets/
```

- **静态数据 vs 运行时状态**严格分离；运行时变化只进存档。
- **唯一稳定 ID**；显示名可变更，**不得作主键**。
- 多库兼容：`2026-27.fdb` / `2012-13.fdb` / `自制数据库.fdb` 均可被同一引擎读取。
- 导入 / 更换数据库**不得自动覆盖存档**。

## 1. 何时使用

- 设计或修改实体、字段、关系。
- 设计或修改 `.fdb` 数据包结构。
- 涉及唯一 ID 策略。
- 划分"静态数据 / 运行时状态"边界。
- 数据库版本、校验与兼容性。
- 换库 / 导入数据库场景。

## 2. 核心原则（项目专属）

1. 引擎内**不得硬编码**任何真实足球数据。
2. **唯一稳定 ID**；显示名不得作主键。
3. **静态（库）与运行时（存档）严格分离**；不得把运行时状态写回数据库。
4. **版本化**；数据错误必须显式报错并给出定位（文件 / 实体 / ID / 字段 / 问题 / 建议修正）。
5. **多库可替换**；引擎不依赖任何单一数据库。
6. **换库不覆盖存档**。
7. 字段级设计必须与制定者确认，**不得自行决定**。

## 3. 必须检查什么（检查清单）

- [ ] 该实体是否有稳定唯一 ID？是否误用名字作引用？
- [ ] 该字段属于**静态库**还是**运行时存档**？边界是否明确？
- [ ] `manifest.json` 是否含版本与引擎兼容声明？
- [ ] 加载时是否做完整性 + 引用完整性校验（悬空 ID、重复 ID、必填缺失）？错误是否可定位？
- [ ] 换库是否会影响既有存档？是否满足"不覆盖"红线？
- [ ] 字段是否满足 `game-systems-logic` 对属性 / 位置 / 角色的模拟需求？
- [ ] 结构是否与 `save-system` 的"引用 + 增量"原则对齐？

## 4. 禁止做什么

- 禁止把真实球队 / 球员 / 联赛数据写进引擎代码。
- 禁止用显示名作主键或实体引用依据。
- 禁止把运行时状态写回数据库。
- 禁止静默忽略数据错误或"能跑就算过"。
- 禁止在导入 / 更换数据库时覆盖存档。
- 禁止自行决定仍标 TBD 的数据设计（已定项见 `DECISIONS.md`）：
  - 实体层级（国家区域、联赛多层、预备/青年队）D1
  - 球员属性粒度与范围 D2
  - 教练/职员是否分离 D3
  - 杯赛与赛事规则表达 D5
  - `.fdb` 物理形态与切分 D8
  - 初始转会入包与版权 D9
  - 校验策略 D11；加载接口形态 D12

## 5. 与其他 Skill 协作

| Skill | 协作方式 |
|---|---|
| `game-architecture` | 分层边界由它定；数据库层作为独立层，Core 经接口访问 |
| `game-systems-logic` | 模拟消费静态数据；本 Skill 保证字段满足模拟需求 |
| `save-system` | 共同维护"静态/运行时"边界与 ID 引用规则 |
| `testing-qa` | 数据库加载/校验/换库用例由它验证 |
| `performance` | 加载方式（全量/流式）与移动端内存由它评审 |
| `mobile-ui-ux` | 数据如何呈现（列表/详情字段）对接 |
| `documentation` | 数据格式与版本变更必须同步文档 |
