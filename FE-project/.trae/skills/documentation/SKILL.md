# Documentation（文档规约 · 项目专属）

> 版本 v1.0（项目定制 · 新建） · 依据：GAME_DESIGN.md / DATABASE_SPEC.md / SIMULATION_SPEC.md / SAVE_SPEC.md / ROADMAP.md
> 本 Skill 是本项目的**文档红线**，不是通用教程。

## 0. 项目事实（前提，不得违背）

- 项目现有 5 份规划文档，落位 `/workspace/docs/`：
  - `GAME_DESIGN.md`（做什么游戏）
  - `DATABASE_SPEC.md`（数据怎么组织）
  - `SIMULATION_SPEC.md`（怎么模拟）
  - `SAVE_SPEC.md`（存档怎么工作）
  - `ROADMAP.md`（先做什么后做什么）
- 文档必须描述**实际实现**，而不是想象中的未来系统。
- 文档必须区分 **`[已定]` / `[TBD]` / `[建议]`** 三种状态。
- 重要架构与数据变更必须**同步**到文档（GAME_DESIGN §0 文档边界）。

## 1. 何时使用

- 完成或修改任一系统之后。
- 发生架构 / 数据结构 / 存档格式 / 数据库格式变更。
- 发现文档与实现不一致。
- 需要记录已知限制。
- 发现文档间存在冲突时（**先上报**）。

## 2. 核心原则（项目专属）

1. **反映真实实现**，不把设想写成已实现。
2. **状态标注**：明确 `[已定]` / `[TBD]` / `[建议]`，不混淆。
3. **变更同步**：架构、数据结构、模拟规则、存档格式、数据库格式、模块职责、已知限制。
4. **冲突先报告**：发现文档之间、文档与既定设计冲突，**先报告，不自行修改**。
5. **数据与逻辑分离**：文档中不得写死真实足球数据。
6. **交叉引用一致**：各 SPEC 的连接处（如静态/运行时边界、ID 引用）须保持一致表述。
7. **无敏感信息**：不含凭据、隐私或一次性任务数据。

## 3. 必须检查什么（检查清单）

- [ ] 本次变更是否已在对应文档体现？
- [ ] 是否区分了 `[已定]` / `[建议]` / `[TBD]`？
- [ ] 是否描述真实实现，而非设想中的功能？
- [ ] 是否记录了**已知限制**？
- [ ] 跨文档引用是否一致（无自相矛盾）？
- [ ] 是否新增了**未获批准**的系统描述？
- [ ] 是否误把 TBD 写成已定？

## 4. 禁止做什么

- 禁止把未实现的功能写成已实现。
- 禁止自行把 `[TBD]` 写成 `[已定]`（须制定者决策）。
- 禁止发现冲突后自行修改（**先报告**）。
- 禁止在文档中写死真实球队 / 球员 / 联赛数据。
- 禁止包含敏感信息或一次性任务数据。
- 禁止为"看起来完整"而虚构文档内容。

## 5. 与其他 Skill 协作

| Skill | 协作方式 |
|---|---|
| `game-architecture` | 结构 / 接口变更必须触发文档更新 |
| `game-systems-logic` | 规则与数值模型变更同步 |
| `database-data-modeling` | `.fdb` 格式与版本变更同步 |
| `save-system` | 存档格式与迁移变更同步 |
| `testing-qa` | 测试结论成文、可交接 |
| `mobile-ui-ux` | 交互规范与已知限制同步 |
| `performance` | 性能指标与瓶颈成文 |

> 本 Skill 是**跨全部 Skill 的收敛点**：任何"已定"的变更若未落文档，视为未完成。
